# Система планирования культурного досуга

Проект ПР1 → ПР2 → ПР3 → ПР5 → ПР6 → ПР7: подбор культурных мероприятий и
сохранение записей посетителей. Консольное приложение (ПР3) дополнено
веб-интерфейсом на Django (ПР5), страницы которого в ПР6 переведены на
шаблоны Django, а в ПР7 получили слой реляционного хранения данных —
базу SQLite и SQL-запросы. Исходные проверки возраста, категории, бюджета, даты и свободных
мест сохранены и по-прежнему работают в консольной версии.

## Назначение

Приложение помогает посетителю выбрать мероприятие по категории, дате,
стоимости билета и возрастному ограничению и записаться на него.

**Консольная версия** (`python main.py`): просмотр, поиск по названию,
фильтрация по категории и сортировка по цене; проверка пригодности
мероприятия для посетителя; добавление и отмена записи; история записей,
посетители и статистика; добавление посетителя и нового мероприятия.

**Веб-интерфейс** (ПР5–ПР7): просмотр списка мероприятий с фильтром по
категории, карточки мероприятия с числом свободных мест, поиск мероприятий по
датам и цене, подбор мероприятий для посетителя, список записей и карточка
записи, страница статистики. Изменение данных
через веб-формы будет реализовано после изучения форм Django.

## Используемые технологии

* Python 3.10+;
* Django 5.2 — веб-фреймворк;
* Django Template Language — шаблоны страниц;
* HTML5, CSS3, JavaScript — разметка, собственные стили и скрипт;
* Bootstrap 5.3 — базовое оформление;
* JSON — исходные данные и хранилище консольной версии;
* SQLite и модуль `sqlite3` — база данных веб-интерфейса, язык SQL;
* pytest — автоматизированные тесты; flake8 — проверка качества кода.

## Объектная модель

| Класс | Данные | Основное поведение |
| --- | --- | --- |
| `Event` | `id`, `name`, `category`, `event_date`, `age_limit`, `ticket_price`, `capacity` | проверка возраста, цены и вместимости, `__str__` |
| `User` | `id`, `name`, `age`, `preferred_category`, `budget` | проверка интереса, `from_data`, `__str__` |
| `Plan` | `id`, ссылки на `Event` и `User`, `is_cancelled` | `cancel`, сериализация, `__str__` |

`Plan` хранит ссылки на два существующих объекта. `cancel()` меняет состояние,
не удаляя объект из коллекции. Условия ПР1 вычисляются по свойствам объектов;
поиск и сортировка коллекций остаются обычными функциями (`events.py`), работа
с файлами — в `storage.py`.

## Веб-интерфейс

Django-проект называется `leisure`, веб-часть разделена на три приложения:

| Приложение | Назначение |
| --- | --- |
| `homepage` | главная страница, страница ошибки 404, общие статические файлы |
| `catalog` | каталог мероприятий (сущность `Event`) |
| `planner` | планы посетителей (сущность `Plan`) |

Приложения названы `catalog` и `planner`, а не `events` и `plans`: пакеты с
такими именами скрыли бы модули `events.py` и `plans.py` консольной версии.
Для пользователей отдельное приложение не создаётся: посетители нужны только
как часть записи, а аутентификация будет рассмотрена позднее.

### Страницы и маршруты

| URL | Имя маршрута | View-функция | Источник данных |
| --- | --- | --- | --- |
| `/` | `homepage:index` | `homepage.views.index` | — |
| `/events/` (`?category=`) | `catalog:list` | `catalog.views.event_list` | SQLite (запросы 1, 2, 4) |
| `/events/search/` | `catalog:search` | `catalog.views.event_search` | SQLite (запрос 5) |
| `/events/recommend/` | `catalog:recommend` | `catalog.views.event_recommend` | SQLite (запросы 3, 6) |
| `/events/<int:event_id>/` | `catalog:detail` | `catalog.views.event_detail` | объекты ПР3 (JSON) |
| `/plans/` (`?status=active`) | `planner:list` | `planner.views.plan_list` | SQLite (запросы 7, 8) |
| `/plans/statistics/` | `planner:statistics` | `planner.views.statistics` | SQLite (запросы 9–13) |
| `/plans/<int:plan_id>/` | `planner:detail` | `planner.views.plan_detail` | объекты ПР3 (JSON) |

Пространства имён задаются переменной `app_name` в `urls.py` приложений.
Если мероприятие или запись не найдены, шаблон выводит сообщение, а view
возвращает статус 404 (`status=404 if event is None else 200`). Любой другой
адрес обрабатывает `handler404` (`homepage.views.page_not_found`, шаблон
`homepage/404.html`); собственная страница видна при `DEBUG = False`.

### Шаблоны Django

View-функции загружают данные (из SQLite или средствами ПР3), готовят контекст
и вызывают `render()`; HTML формируют шаблоны. Функция `page()` из ПР5 удалена.

* `templates/base.html` — базовый шаблон: кодировка, Bootstrap, собственный
  CSS, логотип, навигация, подвал, JavaScript; блоки `title` и `content`;
* `templates/includes/navigation.html` — навигация (Главная, Мероприятия,
  Планы, Статистика) со ссылками `{% url %}`;
* дочерние шаблоны наследуют базовый через `{% extends "base.html" %}` и
  переопределяют блоки;
* включаемые шаблоны: `catalog/includes/event_card.html` (карточка одного
  мероприятия, используется в списке, поиске и подборе; данные передаются
  через `{% include ... with ... %}`) и
  `planner/includes/plan_status.html` (статус записи в списке и на карточке);
* данные передаются через контекст; используются `{% for ... empty %}` и
  `{% if %}`;
* фильтры шаблонов: `length` (число мероприятий и записей), `default`
  (название мероприятия), `date` (дата), `floatformat` (цена билета);
* ссылки формируются только через `{% url 'catalog:detail' event.id %}` и
  другие именованные маршруты.

### Статические файлы

Каталог `homepage/static/homepage/`: `css/style.css` (карточки, статусы,
навигация, логотип), `js/main.js` (текущий год в подвале и подсветка пункта
меню) и `img/logo.png` (логотип). Подключаются тегами `{% load static %}` и
`{% static %}` в `base.html`; проверка: `python manage.py findstatic
homepage/img/logo.png`.

## База данных SQLite (ПР7)

Данные списков, поиска и статистики хранятся в файле `data/culture.sqlite` и
читаются средствами стандартной библиотеки `sqlite3`; Django ORM пока не
используется. JSON-файлы остаются исходными данными консольной версии:
база заполняется из них однократным переносом.

### Структура базы данных

**`events`** — мероприятия

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `name` | TEXT, NOT NULL | название |
| `category` | TEXT, NOT NULL | категория (строчными буквами) |
| `event_date` | TEXT, NOT NULL | дата в формате `ГГГГ-ММ-ДД` |
| `age_limit` | INTEGER, NOT NULL | минимальный возраст (≥ 0) |
| `ticket_price` | REAL, NOT NULL | цена билета (≥ 0) |
| `capacity` | INTEGER, NOT NULL | вместимость (≥ 0) |

**`users`** — посетители

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `name` | TEXT, NOT NULL | имя |
| `age` | INTEGER, NOT NULL | возраст (≥ 0) |
| `preferred_category` | TEXT, NOT NULL | любимая категория |
| `budget` | REAL, NOT NULL | бюджет (≥ 0) |

**`plans`** — записи посетителей на мероприятия

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER, PRIMARY KEY | идентификатор |
| `event_id` | INTEGER, NOT NULL, FOREIGN KEY → `events(id)` | мероприятие |
| `user_id` | INTEGER, NOT NULL, FOREIGN KEY → `users(id)` | посетитель |
| `is_cancelled` | INTEGER, NOT NULL, по умолчанию 0 | 0 — запись активна, 1 — отменена |

Одно мероприятие может иметь много записей, один посетитель — много записей;
каждая запись относится к одному мероприятию и одному посетителю. Первичный
ключ каждой таблицы — `id`; внешние ключи есть в `plans`. Ограничения
`NOT NULL`, `DEFAULT` и `CHECK` описаны в `sql/schema.sql`. Даты хранятся
текстом `ГГГГ-ММ-ДД` — такой формат допускает сравнение и сортировку в SQL.

### Файлы слоя данных

* `sql/schema.sql` — команды создания таблиц и индексов;
* `sql/queries.sql` — 13 проверенных SQL-запросов с комментариями;
* `db/database.py` — `get_connection()` (соединение с `PRAGMA foreign_keys =
  ON`), `create_schema()`, `rows_with_dates()`;
* `db/import_json.py` — перенос данных из JSON (`executemany()`, параметры `?`,
  `commit()`/`rollback()`);
* `data/culture.sqlite` — файл базы данных.

Обновить базу после изменения JSON (например, после работы в консольной
версии) можно командой `python -m db.import_json`: таблицы очищаются и
заполняются заново.

### SQL-запросы

| № | Задача | Элементы SQL | Страница |
| --- | --- | --- | --- |
| 1 | список мероприятий со свободными местами | SELECT, подзапрос, ORDER BY | `/events/` |
| 2 | категории мероприятий | SELECT DISTINCT | `/events/` |
| 3 | список посетителей | SELECT, ORDER BY | `/events/recommend/` |
| 4 | мероприятия выбранной категории | WHERE | `/events/?category=` |
| 5 | поиск по периоду и цене | WHERE, BETWEEN | `/events/search/` |
| 6 | подбор мероприятий для посетителя | JOIN, WHERE, NOT IN | `/events/recommend/` |
| 7 | все записи с мероприятием и посетителем | JOIN трёх таблиц | `/plans/` |
| 8 | только активные записи | JOIN, WHERE | `/plans/?status=active` |
| 9 | общие показатели активных записей | COUNT, SUM, AVG, MIN, MAX | `/plans/statistics/` |
| 10 | записи по мероприятиям | LEFT JOIN, GROUP BY, COUNT | `/plans/statistics/` |
| 11 | сводка по категориям | GROUP BY, MIN, AVG, MAX, SUM | `/plans/statistics/` |
| 12 | мероприятия с не менее чем двумя записями | GROUP BY, HAVING | `/plans/statistics/` |
| 13 | активность посетителей | два LEFT JOIN, GROUP BY, SUM | `/plans/statistics/` |

В запросах приложения значения пользователя передаются только параметрами `?`
(`conn.execute(query, [category])`); подстановка значений в текст запроса не
используется. Строки результата читаются по именам полей благодаря
`conn.row_factory = sqlite3.Row`, поэтому шаблоны обращаются к ним так же,
как к атрибутам объектов (`{{ event.name }}`, `{{ plan.user_name }}`).
Карточки мероприятия и записи пока используют объекты ПР3 и JSON.
Сравнение категорий в SQL чувствительно к регистру (функции регистра SQLite
не работают с кириллицей), поэтому при импорте категории приводятся к
строчным буквам.

## Файлы и данные

```text
TRPF_Project/
├── manage.py            # управление Django-проектом
├── leisure/             # настройки проекта (settings.py, urls.py, wsgi.py, asgi.py)
├── templates/           # base.html и includes/navigation.html
├── homepage/            # приложение: главная, 404, статические файлы
│   ├── templates/homepage/
│   └── static/homepage/ # css/, js/, img/
├── catalog/             # приложение: мероприятия
│   └── templates/catalog/ # список, карточка, поиск, подбор, includes/
├── planner/             # приложение: записи посетителей
│   └── templates/planner/ # список, карточка, статистика, includes/
├── db/                  # database.py (соединение), import_json.py (перенос данных)
├── sql/                 # schema.sql (таблицы), queries.sql (запросы)
├── main.py              # консольное меню (ПР3)
├── models/              # классы Event, User и Plan
├── events.py            # поиск, фильтрация, сортировка и проверки ПР1
├── plans.py             # доступность, создание, отмена и статистика
├── storage.py           # загрузка и сохранение объектов в JSON
├── utils.py             # безопасный ввод
├── data/
│   ├── events.json      # каталог мероприятий
│   ├── users.json       # профили посетителей
│   ├── plans.json       # ссылки и состояние записей
│   └── culture.sqlite   # база данных SQLite (ПР7)
├── tests/               # проверки pytest (консоль и веб)
└── requirements.txt     # Django, pytest, flake8
```

При запуске JSON преобразуется в объекты, при сохранении объекты — в словари.
В `events.json` используются поля `id`, `name`, `category`, `event_date`
(ISO `ГГГГ-ММ-ДД`), `age_limit`, `ticket_price`, `capacity`. В `users.json` —
`id`, `name`, `age`, `preferred_category`, `budget`. Записи в `plans.json`
содержат только `id`, `event_id`, `user_id`, `is_cancelled`. Ссылки
восстанавливаются на конкретные объекты; поврежденный JSON или неизвестный
ID не перезаписываются пустыми данными.

В репозитории лежат демонстрационные данные: пять мероприятий, семь
посетителей и шесть записей (одна из них отменена). Старые записи ПР2 с
`user_name`, `user_age`, `preferred_category`, `budget` читаются без изменения
файлов. Не удаляйте `data/` без резервной копии.

## Запуск и проверка

В каталоге `TRPF_Project` (PowerShell):

```powershell
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py check
python -m db.import_json   # только если нужно пересоздать базу из JSON
python manage.py runserver
```

После запуска откройте `http://127.0.0.1:8000/`. Консольная версия запускается
командой `python main.py`. Проверка кода:

```powershell
pytest -v
flake8 . --extend-exclude=venv
```

Django ORM, формы и авторизация пока не используются. Команда `migrate`
создаёт только служебную базу Django `db.sqlite3` (в репозиторий она не
входит); данные проекта лежат в `data/culture.sqlite`.

## Текущее состояние

На ПР7 данные проекта перенесены из JSON в базу данных SQLite:

* создана база `data/culture.sqlite`, таблицы созданы командами из
  `sql/schema.sql`, определены первичные и внешние ключи;
* данные перенесены скриптом `db/import_json.py`;
* SQL-запросы сохранены в `sql/queries.sql` (13 запросов: выборка, `WHERE`,
  `JOIN`, агрегатные функции, `GROUP BY`, `HAVING`);
* Django-представления получают данные из SQLite и передают их в шаблоны;
* страницы списка мероприятий, поиска, подбора для посетителя, списка записей
  и статистики работают с базой данных;
* консольная версия по-прежнему работает с JSON.

Отложено до следующих работ: подключение базы к Django ORM (модели и
миграции), формы, создание и отмена записей через веб.
